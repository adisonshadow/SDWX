## 一、工艺 / BOM / 工卡 原理速览（口径依据）

> 以下对象口径引自 IPS《修理车间智能排产模块 需求分析与功能架构》，作为后续差距分析的概念基础。

### 1.1 主链路对象

| 对象 | 含义 |
|------|------|
| 车间令号 | 车间生产组织与单台计划的最小单元；一个令号对应一套单台计划 |
| 维修方案 / BOP | 装备 × 修理方式对应的工艺流程；BOP 为其结构化 DAG 载体 |
| 工序 | 可独立发布、报工的最小工艺单元；例行工序投产时实例化为工卡 |
| 工步 | 依附工序；不单独排产 / 报工；检验点控制工序内放行 |
| 工卡 | 工序实例化执行凭证（1 工序 : 1 工卡）；**排产与工位作业的最小对象** |
| 单台计划 / WBS | 令号内全部工卡任务按 BOP 拓扑组织的集合 |

### 1.2 WBS 五层（v0.5 重定义后的语义）

编码规则：`WBS-{生产令号}-L{层级}-{序号}`

| 层级 | 名称 | 职责说明 | 典型示例 |
| --- | --- | --- | --- |
| L1 | 顶层项目 | 整机大修交付总目标 | H130 型飞机左主起落架大修项目 |
| L2 | 全流程大修阶段 | 覆盖拆解→清洗→故检→修理→复装→测试→交付 | 故检与缺陷评估阶段 |
| **L3** | **工序模块**（本系统只含故检和修理部分的标准工序） | 标准工序包（关联维修方案） | 入厂清点、尺寸检测、缺陷评估 |
| **L4** | **工位** | 按工位管理所有工作任务 | 故检（小件） |
| **L5** | **工卡（含执行数据）** | 可派工、可报工的最小单元 | 检测工卡和外筒内径三坐标等测量数据 |

> ⚠️ 关键变化：**L4 = 工位**（带 `stationCode`），**L5 = 工卡**。这是 v0.5 工卡路由与工艺展示的层级依据。

### 1.3 工艺信息的三类载体

- **processRequirement**（文字指导）：工序 / 工位 / 工卡级的文字性、段落性作业指导
- **inspectionItems**（结构化检测项 + 公差）：故检副屏、自动采集与判异的**直接数据源**
- **processResources**（文档 / 视频 URL）：工艺规程 / 图纸 / 教学视频，由 PCS / CAPP 提供访问地址（工控网可访问），不随工卡打包传输

## 三、分组详细差距

### 3.1 通用基础：数据模型与术语对齐

#### G1 — WBS 五层语义未落地

**v0.5 要求**（3.4.5.a）：L3 = 工序模块、L4 = **工位**（带 `stationCode`，如 `GJ-XJ-01`）、L5 = **工卡**（含执行数据）。本系统接收 PCS 下发的 WBS 子树后「按 L4 `stationCode` 将工卡路由至对应工位；在工卡详情展示 L5 的 `processRequirement` 与 `processResources` 链接」。

**现状**：
- `WbsNode`（`packages/shared/src/types.ts:77`）仅有扁平字段：`wbs_code`、`parent_id`、`node_level`、`process_code`、`process_name`、`process_description`、`process_resources`、`estimated_minutes`、`workstation_type`。
- **缺** `stationCode`（L4 工位编码）、`children`（树结构）、`processRequirement`（与 `process_description` 并存的工艺要求正文）、`standardBasis`、`inspectionToolCode`、`planWorkHours`。
- `WorkCardDetail.tsx` 取 `wbs_node` 后只渲染 `process_name` / `process_description` / `estimated_minutes`，未按 L3→L4→L5 树状呈现工艺归属。

**待办**：
1. 扩展 `WbsNode`：新增 `stationCode`、`processRequirement`、`standardBasis`、`inspectionToolCode`、`planWorkHours`、`inspectionItems?`、`children?: WbsNode[]`、`dataHistory?`。
2. `WorkCardDetail.tsx` 增加「工艺路线」视图：从工卡的 `wbs_node` 向上回溯到 L3 工序模块 / L4 工位，展示归属链；在 L5 节点展示 `processRequirement` / `processResources`。
3. BFF `fetchWorkCardDetail` 返回需携带 WBS 子树（至少 L3 / L4 / L5）。

#### G2 — 检测项字段不对齐（**P0 阻断联调**）

**v0.5 要求**（3.4.5.c）：`inspectionItems` 字段含 `dataCollectionType`（`auto` | `manual`）、`manualOnly`、`requirePhoto`、`partRef`、`feature`、`nominalValue`、`upperTolerance`、`lowerTolerance`、`unit`、`inspectionToolCode`。

**现状**：
- `InspectionItem`（`types.ts:104`）用 `item_type`、`inspection_method`（无明确枚举）、`measure_tool_code`，**缺** `dataCollectionType`、`manualOnly`、`partRef`、`feature`。
- `InspectionBoard.tsx:103` 用 `item.inspection_method === 'auto'` 判定数采 vs 人工判定；公差字段 `nominal_value` / `upper_tolerance` / `lower_tolerance` 已对齐。

**待办**：
1. `InspectionItem` 新增 `data_collection_type?: 'auto' | 'manual'`、`manual_only?: boolean`、`part_ref?: string`、`feature?: string`。
2. 判定逻辑切换为 `data_collection_type === 'auto'`（`InspectionBoard.tsx:103`），保留 `inspection_method` 向后兼容或迁移。
3. `manualOnly=true` 项渲染为人工合格 / 不合格单选，不绑数采。

#### G3 — ProcessResource 缺 resourceId

**v0.5 要求**（3.4.5.d）：`resourceId` 为资料唯一标识（必填）。

**现状**：`ProcessResource`（`types.ts:96`）缺 `resourceId`。

**待办**：补 `resource_id?: string` 字段；`WorkCardDetail.tsx` 的 `normalizeProcessResources`（`:28`）同步兼容读取。

#### G4 — 工卡初检 / 复检来源未区分

**v0.5 要求**（2.4）：故检支持「初检 + PCS 复检工卡」两种场景，复检工卡由 PCS 在修理完成后新增下发。

**现状**：`WorkCard.source`（`types.ts:55`）字段存在，但列表 / 详情 UI 未做初检 / 复检标识，操作员无法区分。

**待办**：`WorkCardList` 卡片 + `WorkCardDetail` 头部增加「初检 / 复检」标签（基于 `source` 或新增 `inspection_round` 字段）。

#### G10 — 测量工具状态监控 + 异常报警

**待办**：
1. `useOpWs` 增加 `tool.status` / `tool.alarm` 事件分发。
2. `tool.alarm` 触发报警弹窗（明确故障工具 + 异常类型）。

**待办**：实现齐套校验逻辑 —— 工卡 `WorkCardPart[]` 与已填充 slot 比对，弹出齐套提示或缺项明细。

#### G17 — 分拣结果回写（🔴）

**v0.5 要求**（3.2.2）：操作员确认齐套后提交分拣执行结果。

**现状**：`WorkCardPart.sorted_quantity`（`types.ts:210`）从不回写；分拣 toggle 仅本地状态。

**待办**：分拣完成 → `updatePart(partId, { sorted_quantity, status })` 回写；齐套确认 → `submitWorkCard`。

### 3.7 故检副屏（3.2.3）

#### G18 — 处置分类打码（不持久化）

**现状**：`InspectionDisposal.tsx`（新增文件）已实现三分类处置 + `suggestDisposal` 建议生成 + CODE128 条码生成（`buildBarcodes`）+ 打印按钮，**但全部本地状态**：

- 未调用 `updatePart({ disposal_result })` 回写零件处置结论。
- 条码打印是 stub（`InspectionDisposal.tsx:317`）。

**待办**：
1. 处置确认 → 调用 `updatePart` 写 `disposal_result` + `disposal_remark`。
2. 委外 → `createOutsource`；报废 → `createScrap`；厂内修理 → `createRepairRecord`。
3. 条码打印接实际打印（Electron `webContents.print`）。

#### G19 — 大件 vs 小件故检处置差异

**v0.5 要求**（2.4.2）：大零件故检不合格时**不在修理工位执行厂内修理** —— 流转至修理工位仅完成委外登记、打印委外修理单，随后随大件 AGV 转运至收发工位进入委外发运。小件则可委外 / 修理 / 报废。

**现状**：`renderOpBoard.tsx:21` 对 `inspection_small` 和 `inspection_large` 渲染**同一个 `InspectionBoard`**，未按工位类型区分处置路径。`InspectionDisposal` 三分类对所有故检工位都开放「厂内修理」选项。

**待办**：`InspectionBoard` / `InspectionDisposal` 按 `workstationType` 区分 —— `inspection_large` 时禁用「厂内修理」选项，仅允许委外登记 + 打印委外单。

#### G20 — 扫码定位零部件

**v0.5 要求**（2.4.3 步骤 2 / 3.2.d）：操作员手持扫码枪扫描零部件条码，系统定位并高亮对应检测任务区域。

**现状**：`InspectionBoard` 无扫码触发入口；`InspectionItem.partRef`（即 `part_code`）字段可用于定位但 UI 未实现。

**待办**：`InspectionBoard` 增加「扫码定位」按钮 → 扫码 → 按 `part_code` 过滤 / 高亮该零件的检测项。
